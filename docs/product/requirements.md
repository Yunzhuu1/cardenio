## 1. 背景与问题陈述

小说改编为剧本不是简单的文本改写，而是**两种媒介语言之间的翻译**。小说擅长心理描写、叙述声音、内心独白与文学性表达；剧本需要可表演、可拍摄、可排演的场景、动作、对白与冲突。

作者在自行改编时面临的真实痛点：

1. **媒介落差难跨越**：大段心理活动、全知叙述、不可靠叙述者无法直接视觉化。
2. **重复劳动消耗创作力**：格式转换、信息搬运、场景拆分占用大量精力。
3. **对 AI 黑盒的不信任**：担心 AI「悄悄加戏」「丢了原作的魂」「擅自定调」。
4. **打磨成本高**：改编只发生一次，打磨发生几百次，缺乏高效的局部修改工具。
5. **数据安全焦虑**：未发表稿件是核心资产，不敢上传到来路不明的服务。

本产品的核心命题：**做一个懂小说、懂剧本、懂两种语言落差，并始终把决定权交还给作者的「副驾驶」**，而非一键出稿的黑盒。

## 2. 产品目标与非目标

### 2.1 目标

- **G1** 让作者导入 3 个章节以上的小说文本，获得结构化（YAML）、可编辑、可继续打磨的剧本初稿。
- **G2** 在转换前先「读懂」小说并让作者确认，确保理解正确再改编。
- **G3** 把媒介翻译的关键决策（心理外化、删减合并、加戏）显性化、可控、可溯源。
- **G4** 提供以「局部重生成」为核心的高效打磨编辑体验。
- **G5** 在数据隐私、风格保真、导出自由上建立作者信任。

### 2.2 非目标（本期不做，避免范围蔓延）

- **NG1** 不做一键生成「最终成稿」；只产出可打磨的初稿。
- **NG2** 不替代专业剧本软件（如 Final Draft）做后期排版与制片管理，只做导出对接。
- **NG3** 不做整本长篇（几十万字）连续改编的工程化保障（列入未来规划，见 §12）。
- **NG4** 不做自动分镜导演化（景别/运镜仅作为可关闭的「建议」，不默认输出）。
- **NG5** 不做多人实时协作。

## 3. 目标用户与画像

| 画像 | 描述 | 核心诉求 |
| --- | --- | --- |
| 资深小说作者（主画像） | 有成熟作品与稳定文风，重视原作气质与版权 | 风格保真、可控、可溯源、数据安全 |
| 网文作者 | 篇幅大、更新快，希望快速试改编 | 效率、长文处理、局部重写 |
| 剧本创作爱好者 / 学习者 | 想学习小说到剧本的转换方法 | 改编取舍报告的可解释性 |
| 内容团队 | 需要快速获得剧本初稿用于评估 | 速度、可导出对接 |

第一版优先服务**中文小说作者**，UI / 原文 / 输出语言从一开始解耦（见 NFR-7）。

## 4. 核心设计原则（研发决策的判断基准）

这些原则在需求取舍、交互设计、Prompt 设计时具有最高优先级；当具体需求与原则冲突时，以原则为准并提 Issue 复审。

- **P1 先理解，再改编**：必须先产出作品理解与人物档案并经作者确认，才进入剧本生成。
- **P2 作者可控**：所有 AI 产物可检查、可修改、可回退、可分支；决定权永远在作者。
- **P3 媒介翻译而非信息搬运**：心理/叙述内容必须被「翻译」为动作、对白、环境、声音、潜台词，而非删除或硬塞台词。
- **P4 一切可溯源**：每个场景、每句台词都能定位回原文出处。
- **P5 AI 产物可区分**：原文已有 vs AI 推断/新增，必须显式标记，便于重点复查。
- **P6 敢于留白**：AI 不确定的地方宁可留 `TODO` 让作者填，不用平庸内容填满。
- **P7 保留原作气质**：风格、情绪基调由作者设定，AI 不擅自定调。
- **P8 中间产物可编辑**：理解、档案、大纲、剧本均为可编辑工件，不隐藏在单一生成步骤背后。

## 5. 端到端主流程

```text
导入小说
  └─> 预处理与结构识别（章节/视角/时态）
        └─> 作品理解报告（可编辑，需确认）        ← P1
              └─> 人物档案（可编辑，需确认）        ← P1
                    └─> 作者意图锁定 + 改编方向选择   ← P2/P7
                          └─> 分场大纲（可编辑）
                                └─> 剧本初稿（YAML）  ← P3/P4/P5
                                      ├─> 双栏对照编辑 / 局部重生成 / 版本分支
                                      ├─> 改编取舍报告
                                      └─> 导出（DOCX / PDF / Fountain ...）
```

每个环节都是一个**可保存、可回到、可编辑**的工件（artifact），共同构成一个「改编项目」。

## 6. 功能需求详述

### FR-1 导入与预处理 · `Must`

**描述**：支持作者导入至少 3 个章节的小说文本，并完成结构化预处理。

**子需求**：
- FR-1.1 输入方式：直接粘贴文本、按章节录入、TXT 导入、DOCX 导入（`Must`）；RTF / PDF / EPUB（`Could`，未来）。
- FR-1.2 章节切分：自动识别章节边界（标题、分隔符），允许作者手动调整切分点。
- FR-1.3 字数与章节计数：实时显示，校验「≥3 章」门槛并给出提示。
- FR-1.4 字符与编码清洗：统一全/半角、去除导入产生的乱码与多余空白，保留原文换行语义。

**验收标准**：
- 导入 3 章 TXT/DOCX 后，系统正确识别章节数与各章字数，作者可手动合并/拆分章节。
- 导入内容在「原文视图」中与源文件一致，无字符丢失。

---

### FR-2 作品理解（转换前的「读懂」）· `Must`

**描述**：在改编前生成作品理解报告并**要求作者确认或修改**，修改后的内容作为后续改编依据。对应 P1。

**输出字段**（与 project-context 对齐）：
- 一句话故事核（logline）、故事简介、核心主题
- 主角目标、主角恐惧、主要矛盾
- 情绪基调、叙事风格（**风格指纹**，用于全程保持文风，对应 P7）
- 叙事视角与时态识别（第一人称内心独白 / 全知 / 不可靠叙述者）
- 改编优势、改编难点

**关键子需求**：
- FR-2.1 **视角与时态标记**：对无法直接视觉化的段落（如大段心理独白）主动标记 `non_visualizable`，并在后续生成时触发外化处理（关联 FR-7.1）。**严禁默默编造台词糊弄。**
- FR-2.2 **风格指纹采样**：对原文文风采样（冷硬/抒情/幽默等），作为全程生成的风格约束，避免套通用「编剧腔」。
- FR-2.3 理解报告全字段可编辑；编辑后版本作为「事实源」向下游传递。

**验收标准**：
- 报告各字段均可编辑并保存；未确认时不能进入下一步（强制 P1）。
- 含大段心理描写的章节，报告中能列出至少一处 `non_visualizable` 标记。

---

### FR-3 人物档案 · `Must`

**描述**：自动提取主要人物并生成可编辑档案，用于后续一致性检查（关联 FR-9.4）。

**输出字段**：姓名、身份、性格、**说话方式（voice 指纹）**、核心欲望、核心恐惧、人物关系、人物弧光、不可违背的人设规则（`hard_rules`）。

**子需求**：
- FR-3.1 人物分类：主角 / 配角 / 仅被提及未出场，分别标注。
- FR-3.2 人物关系图：结构化存储关系，供大纲与一致性检查引用。
- FR-3.3 档案全字段可编辑；`voice` 与 `hard_rules` 在台词生成时作为硬约束。

**验收标准**：
- 提取出原文出现的全部具名主要人物，分类正确率经人工抽检可接受。
- 修改某人物 `hard_rules` 后，后续生成与一致性检查引用的是修改后的值。

---

### FR-4 作者意图锁定 · `Must`

**描述**：正式生成前收集作者意图，**意图优先级高于 AI 自由发挥**（P2）。

**收集项**：最想保留的内容、不能删除的情节、不能合并的人物、必须保留的台词、作品情绪底色、是否允许新增桥段、是否允许改变故事顺序、是否允许调整结局、目标剧本类型。

**验收标准**：
- 当作者勾选「不允许新增桥段」时，生成结果不得包含 `ai_inferred` 的新增剧情节点（仅允许媒介翻译层面的外化）。
- 「必须保留的台词」在生成剧本中逐字出现，并标记来源为原文。

---

### FR-5 改编方向选择 · `Must`（部分方向 `Should`）

**描述**：提供改编方向预设，影响生成策略与节奏。

**方向**：忠实改编、影视化增强、短剧模式（`Must`）；电视剧、电影、舞台剧模式（`Should`/`Could`）。

**验收标准**：
- 不同方向对同一段落产出可观察到的差异（如短剧模式节奏更快、场次更短）。
- 方向选择与作者意图冲突时（如「忠实改编」+「允许调整结局」），给出冲突提示。

---

### FR-6 分场大纲 · `Must`

**描述**：先把小说拆分为剧本场景并生成大纲，作者确认/编辑后再生成正文（P1、P8）。

**每场字段**：场景标题、来源章节（`source_ref`）、地点、时间（内/外、昼/夜）、出场人物、场景目标、场景冲突、情绪基调、主要事件、人物关系变化、伏笔信息、场景结尾状态。

**子需求**：
- FR-6.1 **合并建议而非擅自删除**：识别可合并的过场并给出**建议**，由作者决定是否采纳（P2/P3）。
- FR-6.2 大纲可增删场景、调整顺序、修改字段。
- FR-6.3 每场保留 `source_ref` 溯源到原文段落（P4）。

**验收标准**：
- 每个场景均含非空 `source_ref`，可点击跳转到原文对应段落。
- 合并/删除以「建议」形式呈现，未经作者确认不改变大纲结构。

---

### FR-7 剧本生成：媒介翻译 · `Must`

**描述**：基于大纲生成剧本初稿，核心是把小说语言「翻译」为剧本语言（P3）。这是产品价值的关键环节。

**子需求**：
- FR-7.1 **心理活动可视化建议**：遇到大段内心戏，**不删除**，提供多种处理方案供作者选择：画外音（V.O.）、转为具体动作、转为对话外化、保留为给导演的注释。默认给出 1 个主推方案 + 备选，并标记 `ai_inferred`。
- FR-7.2 **叙述描写 → 场景说明 + 镜头提示**：环境/氛围描写转为场景说明；景别/运镜**仅作为可一键关闭的「建议」**，默认可按用户设置开关（关联 NG4）。
- FR-7.3 **对白剧本化**：把书面化对话提炼为口语化、有节奏、能「说出口」的台词，同时保留人物 `voice` 指纹与口头禅（引用 FR-3）。
- FR-7.4 **冗余压缩与节奏重组**：识别必须保留的剧情节点 vs 可合并过场，给出合并建议（关联 FR-6.1）。
- FR-7.5 **加戏强标注**：任何原文没有、AI 脑补的台词或动作，必须 `flag: ai_inferred` 并高亮（P5）。这是**底线需求**。
- FR-7.6 **潜台词与情绪显性化**：为台词/场景标注 `subtext` 与 `mood`。

**剧本内容**：场景标题、动作描写、人物对白、必要旁白、停顿、转场、关键道具、场景结尾。

**验收标准**：
- 含大段心理独白的场景，输出至少一个外化方案且标记 `ai_inferred`，原文心理内容不被静默丢弃。
- 凡 AI 新增内容均带 `ai_inferred` 标记，UI 可高亮筛选。
- 作者意图中「必须保留的台词」逐字出现且标记原文来源。

---

### FR-8 结构化输出：YAML 数据模型 · `Must`

**描述**：剧本以 YAML 为底层结构化存储，结构需「专业且可改」。完整 Schema 见 §7。

**关键约束**：
- FR-8.1 每个场景、每句台词均含 `source_ref`（章节 + 段落区间），支持溯源跳转（P4）。
- FR-8.2 每个节拍/台词可带 `flag`（`ai_inferred` / `from_source` 等），区分来源（P5）。
- FR-8.3 关键字段 `subtext`、`mood`、`voice`、`hard_rules` 必须在 Schema 中一等公民化。
- FR-8.4 YAML 须可被产品稳定解析与回写，编辑不破坏结构（往返一致：parse → edit → serialize 不丢字段）。

---

### FR-9 编辑体验（打磨工作台）· `Must`（分支/一致性部分 `Should`）

> 转换只发生一次，打磨发生几百次。编辑体验比转换算法更决定留存。

- FR-9.1 **双栏对照视图** `Must`：左原文、右剧本，**滚动联动 + 互相高亮**，改剧本时始终看得到原文出处。
- FR-9.2 **局部重生成** `Must`（核心交互）：选中单场/单段，用自然语言指令（如「这场太平淡，把冲突往前提」「口语化一点」「把内心戏改成动作」）只重写该块，不动其他。重生成需参考前后场景、人物档案、作者意图、整体剧情。
- FR-9.3 **版本与分支** `Should`：同一场戏可并存多个方向（如「温情版」「冷峻版」），可分支、对比、回滚。
- FR-9.4 **一致性守护** `Should`：改人物名全局同步；改人设后检测并提示冲突台词（引用 FR-3 档案）。
- FR-9.5 **所见即所得 + 源码双视图** `Must`：默认呈现标准剧本排版（中文剧本格式），YAML 在底层；需要时可切到原始 YAML 手改。作者不应被 YAML 语法卡住。
- FR-9.6 **留白友好** `Must`：不确定处以 `TODO` 标记呈现，可定位、可筛选（P6）。

**验收标准**：
- 局部重生成只改变选中块，其余场景的内容与版本 ID 不变。
- 双栏视图滚动联动，点击剧本场景能高亮对应原文段落。
- 人物改名后，全剧本对白与动作中的指代同步更新。

---

### FR-10 改编取舍报告 · `Must`

**描述**：每次生成完整剧本后产出报告，让改编决策可解释（P3/P5）。

**内容**：保留了哪些关键情节、删除了哪些、合并了哪些场景、新增了哪些桥段、哪些心理描写被改成动作/对白、哪些台词来自原文、哪些是 AI 新写、哪些伏笔被保留、哪些建议作者重点复查。

**验收标准**：
- 报告中每条「删除/合并/新增/改写」均可定位到对应场景或原文段落。
- 报告统计与剧本中的 `flag` 标记一致（无遗漏新增内容）。

---

### FR-11 导出 · `Should`（Fountain `Must` 优先）

**描述**：导出到通用格式，避免生态锁定。

- 优先：DOCX、PDF、Fountain（`Should`，其中 Fountain 优先打通以对接专业软件）。
- 未来：FDX（Final Draft）、RTF、Markdown（`Could`）。
- 中文剧本默认采用符合中文创作习惯的排版（见 project-context 示例）；英文剧本对齐传统 screenplay 格式。

**验收标准**：
- 导出的 Fountain/DOCX 在目标软件中可正常打开，场景标题、人物、对白、动作层级正确。

## 7. 数据模型 / YAML Schema 规范

以下为剧本工件的规范化结构，研发应据此定义类型与校验。字段命名为最终契约，新增字段需走 Schema 评审。

```yaml
screenplay:
  meta:
    project_id: "prj_xxx"
    title: "..."
    logline: "..."                # 一句话故事核
    adaptation_direction: faithful # faithful | cinematic | short_drama | tv | film | stage
    ui_language: zh-CN
    source_language: zh-CN
    output_language: zh-CN
    style_fingerprint: "克制、冷硬、意象密集"  # 风格指纹，全程约束
    version: "v3"
    parent_version: "v2"          # 用于分支/回滚
  characters:
    - id: lin_wan
      name: "林晚"
      role: protagonist           # protagonist | supporting | mentioned
      voice: "克制、爱用反问"       # 说话风格指纹
      desire: "找回父亲的真相"
      fear: "再次被抛弃"
      arc: "从回避到直面"
      relations:
        - to: lin_fu
          type: "父女"
          change: "由疏离到和解"
      hard_rules:                  # 不可违背的人设规则
        - "从不主动示弱"
  scenes:
    - id: sc_012
      heading:
        int_ext: INT               # INT | EXT
        location: "旧书店"
        time: NIGHT                # DAY | NIGHT | DAWN | DUSK
      source_ref:                  # 溯源（必填）
        chapter: 2
        paragraphs: [45, 51]
      synopsis: "林晚发现父亲的信"
      goal: "揭示父亲秘密"          # 场景目标
      conflict: "真相与逃避的撕扯"   # 场景冲突
      mood: "压抑、悬而未决"         # 情绪基调
      foreshadowing: ["父亲的怀表"]  # 伏笔信息
      relation_changes:
        - characters: [lin_wan, lin_fu]
          change: "信任出现裂缝"
      ending_state: "林晚握紧日记，决定追查"
      beats:                       # 场景节拍序列
        - type: action
          text: "林晚拂去书脊的灰，抽出一本日记。"
          subtext: "她其实早就知道它在这里。"
          source_ref: { chapter: 2, paragraphs: [46] }
          flag: from_source        # from_source | ai_inferred
        - type: dialogue           # dialogue | voice_over | off_screen
          character: lin_wan
          parenthetical: "(声音发抖)"
          dialogue: "原来你一直都……"
          source_ref: { chapter: 2, paragraphs: [48] }
          flag: from_source
        - type: note               # 给作者/导演的注释
          text: "原文为大段内心独白，建议用画外音处理，可替换为动作。"
          flag: ai_inferred
          options:                 # 心理外化的多方案（FR-7.1）
            - kind: voice_over
              text: "（V.O.）这一次，我不会再回头。"
            - kind: action
              text: "林晚合上日记，吹熄了灯。"
        - type: todo               # 留白标记（FR-9.6）
          text: "此处需作者补充父女对峙的关键台词。"
  shot_hints:                      # 可一键关闭的镜头建议（FR-7.2，默认按设置）
    enabled: false
```

**研发须知**：
- `source_ref`、`flag` 为高频校验字段：序列化/反序列化往返必须无损（关联 FR-8.4）。
- `flag` 仅两类来源语义：`from_source`（原文已有）、`ai_inferred`（AI 推断/新增）；UI 据此高亮与筛选。
- `style_fingerprint`、`voice`、`hard_rules` 在生成与一致性检查中作为约束输入，不可丢失。

## 8. 非功能需求

### NFR-1 数据隐私与安全 · `Must`
- 明确告知数据存储位置、是否用于模型训练；提供「不用于训练」的明确承诺与设置。
- 规划私有化/本地化处理能力（至少在隐私政策与架构上预留），降低未发表稿件上传的顾虑。
- 传输与存储加密；项目级数据隔离。
> 这是信任底线：不过关则再好用也不会被采用。

### NFR-2 风格保真 · `Must`
- 全程以 `style_fingerprint` 与人物 `voice` 约束生成，避免「编剧腔」覆盖原作气质（P7）。
- 暗黑/悬疑等基调不得被默认改成温吞网剧腔；基调由作者设定。

### NFR-3 长文一致性（诚实披露）· `Should`
- 三章为起点，目标是整本几十万字。需在长文下保持人物、伏笔、关系前后一致。
- 当超出可靠处理长度时，**如实提示**当前限制与一致性风险，不静默截断（关联「无静默上限」原则）。

### NFR-4 可解释与可追溯 · `Must`
- 所有改编决策可经由「改编取舍报告 + `flag` + `source_ref`」三者交叉追溯。

### NFR-5 性能与响应 · `Should`
- 局部重生成优先保证低延迟（只处理选中块）。
- 整本初稿生成可异步、可分阶段产出，提供进度反馈。

### NFR-6 可靠性 · `Must`
- 中间工件（理解/档案/大纲/剧本/报告）自动保存、可恢复，避免长流程中断丢失。
- 版本与分支数据不可因局部操作被破坏。

### NFR-7 国际化架构 · `Must`（实现 `Should`）
- 从一开始区分 **UI Language / Source Language / Output Language** 三者。
- 第一版聚焦简体中文，但数据模型与文案不得硬编码语言假设。

### NFR-8 导出开放性 · `Should`
- 不锁定生态：保证可导出到通用、可被第三方软件读取的格式（Fountain 优先打通）。

## 10. MVP 范围与优先级

### 10.1 MVP 必做（`Must`）
FR-1 导入预处理、FR-2 作品理解（含视角标记/风格指纹）、FR-3 人物档案、FR-4 作者意图、FR-5 改编方向（忠实/影视化/短剧）、FR-6 分场大纲、FR-7 剧本生成（含心理外化、加戏标注、对白剧本化）、FR-8 YAML 结构与溯源、FR-9.1/9.2/9.5/9.6 编辑核心（双栏对照、局部重生成、所见即所得、留白）、FR-10 改编报告；NFR-1/2/4/6/7。

### 10.2 MVP 后尽快（`Should`）

### 10.3 端到端验收（Demo 级）
作者导入 3 章中文小说后，可依次获得**可编辑**的作品理解、人物档案、分场大纲、剧本初稿（YAML，含 `source_ref` 与 `ai_inferred` 标记）、改编报告，并能在双栏视图中对单场执行一次自然语言局部重生成且只改动该场。

## 12. 术语表

| 术语 | 含义 |
| --- | --- |
| 工件（artifact） | 流程中可保存、可编辑、可回退的中间产物（理解/档案/大纲/剧本/报告） |
| 媒介翻译 | 把小说语言（心理/叙述）转化为剧本语言（动作/对白/潜台词）的过程 |
| 风格指纹 | 对原文文风的结构化采样，全程约束生成 |
| `source_ref` | 场景/台词溯源到原文章节与段落的引用 |
| `ai_inferred` | 标记原文没有、由 AI 推断或新增的内容 |
| 局部重生成 | 仅对选中场/段按自然语言指令重写，不影响其余内容 |
| 潜台词（subtext） | 台词字面之下的真实意图 |
